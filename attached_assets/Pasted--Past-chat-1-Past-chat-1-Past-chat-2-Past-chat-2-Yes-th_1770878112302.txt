## 1) Whole-system assessment (what we measure)

Think of this as a 60–90 minute “readiness sweep” that outputs a single artifact: **STATE.md** (current truth) + a **Top-10 punchlist**.

### A. Build & repo health

Run these and record results:

* `npm run typecheck` (or `tsc --noEmit`)
* `npm test` (even if small right now)
* `npm run lint`
* `npm run build`
* “fresh clone” sanity (clean install + run)

**Pass condition:** clean, repeatable, no “works on my machine” assumptions.

### B. Pipeline invariants (core correctness)

You want explicit invariants for each stage:

* **Adapter boundary:** wire format vs internal format stays separated (you already fixed the key one).
* **Policy enforcement:** deterministic outcome for same inputs; no hidden randomness.
* **Observation handling:** “unknown observationType” fails closed, not open.
* **Violation logging:** logs never invent fields; they only report what exists.

**Deliverable:** `INVARIANTS.md` (short, brutal, testable statements).

### C. Audit trail (tamper-evidence you can defend)

You already hardened the chain — now verify it’s *operationally defendable*:

* **Canonical payload** is single-sourced (`auditPayloadV1()`): ✅ you called this out.
* **Partial verification** is detectable (limit < total): ✅ you implemented.
* **DB transaction semantics** are correct for your runtime DB (Postgres vs SQLite differences).
* **Threat model** exists and is narrow/explicit (what it does NOT protect against matters as much as what it does).

**Deliverable:** `THREAT_MODEL_AUDIT.md` (one page).

### D. Operability: logging, metrics, and failure visibility

Add (or confirm) these:

* A single “request correlation id” threaded through adapter → policy → audit.
* Structured logs (JSON) for key events.
* Counters:

  * policy violations by observationType
  * adapter failures by provider
  * audit append success/failure
  * verify partial/full counts

**Deliverable:** a basic “Operator View” page or endpoint that reports counts.

### E. Security posture (basic, non-negotiable)

* Secrets never logged.
* Rate limiting at the ingress.
* Input size limits (body + field-level).
* “Dangerous content” handling consistent with your refusal posture.

**Deliverable:** `SECURITY.md` (small, concrete).

## 2) The next sprint (what we actually *do*)

If you want maximum leverage, do this in order:

### Step 1 — Freeze the interface contracts

Lock down:

* `AdapterRequest` (wire)
* internal observation shape (`observationType`)
* `LlmObservation` (wire/storage)
* audit append/verify public return types

**Why:** once contracts are stable, everything else becomes testable and non-drifty.

### Step 2 — Add “golden tests” (determinism + invariants)

Minimal but high value:

1. **Audit chain golden test**

   * append 3 events → verify ok
   * mutate 1 byte in stored payload → verify fails at seq N
2. **Policy enforcement golden test**

   * same rawContent + same observationType → identical decision + identical audit payload
3. **Adapter boundary test**

   * confirm `observation_type` never appears in internal logic objects (except construction edges)

This is where you stop regressions permanently.

### Step 3 — CI so you can’t regress at 2am

Add GitHub Actions (or equivalent):

* typecheck
* lint
* tests
* build
* (optional) simple security scan

### Step 4 — “Operator-grade verification endpoint”

If you don’t already have it, create:

* `GET /api/audit/verify?limit=...`
  Returns:
* `ok`, `partial`, `totalEvents`, `checkedEvents`, `firstBadSeq`, `headHash`, etc.

Then surface it in UI: a **single banner** that tells the truth instantly.

### Step 5 — Write the “STATE.md” and “What’s forbidden” page

This is the piece that prevents feature-myth drift:

* **Implemented**
* **Explicitly forbidden**
* **Out of scope**
* **Known risks**
* **Next hardening items**

It becomes your internal constitution for the repo.
