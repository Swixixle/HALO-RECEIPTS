## 1) External anchoring MVP: make it a true separate trust boundary

### A. S3 Object Lock (WORM) – what makes it *actually* a trust boundary

To defeat “DB superuser rewrites everything,” your S3 anchor must satisfy:

**Minimum bar**

* Bucket has **Object Lock enabled**
* Retention enforced (pilot: governance mode acceptable; production: consider compliance mode)
* **Separate AWS account** (or at minimum, separate IAM boundary) from the DB admin
* Write role can `PutObject` but cannot shorten retention / delete / overwrite

**What auditors will probe**

* “Can an admin in *this* account still bypass Object Lock?”

  * Governance mode *can* be bypassed by principals with `s3:BypassGovernanceRetention` if allowed.
  * So the policy must ensure DB-admin-equivalent principals do **not** have bypass capability.

**Your MVP story should be explicit**

* “DB superuser cannot modify S3 anchors; S3 account policy denies bypass. Reconciliation requires collusion.”

### B. RFC3161 TSA – what makes it legally legible

Minimum bar:

* Timestamp token over `anchor_hash`
* Verifier validates:

  * token signature
  * token message imprint matches `anchor_hash`
  * token time is present and parseable
  * token chain anchors to a pinned TSA root/intermediate (or an allowlisted TSA cert fingerprint set)

**What you don’t need for MVP**

* Fancy multi-TSA quorum
* OCSP live checks (you can document as “optional online enhancement”)

## 3) Verifier output: make anchors first-class in the verdict

Don’t bury anchoring under “additional info.” Make it a **separate verdict line**:

* ✅ **Integrity**: chain replay + checkpoint signatures OK
* ✅/⚠️ **Anchoring**: (S3: present/verified) (TSA: present/verified)
* ⚠️ **Anchoring coverage**: 3/3 checkpoints anchored (S3+TSA)

And if an anchor is missing:

* Integrity can still be ✅
* Anchoring becomes ⚠️ and the verifier should say exactly what that means:

  * “DB superuser rewrite resistance is reduced; pack is still internally consistent.”

That’s the “honest operator-grade” posture you’ve been nailing.

## 4) Determinism / reproducibility gate: fix the only common trap

You already hit the big gotcha: **ephemeral keys** (or anything timestamped) will break byte-for-byte reproducibility.

The correct pattern is:

* Determinism gate must rebuild **the verifier zip** and compare hashes
  **without including** any run-specific artifacts (tokens, anchors, proof packs).
* If you also want determinism for proof bundles, you need:

  * normalized ZIP timestamps
  * stable file ordering
  * deterministic key material **only for that gate** (fixture key)
  * and you must exclude TSA tokens by design (they are time-bound and non-deterministic)

**Recommendation:**
Keep reproducibility gate focused on the verifier release artifact only. Proof bundles should be **signed + hashed**, not byte-reproducible.

## 5) Key management: one more hardening move that pays dividends

1. **kid must be present in every checkpoint**
2. Verifier must refuse to “guess” keys:

This prevents the most common “silent accept” failure mode during rotations.
