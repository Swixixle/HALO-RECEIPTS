If we’re going “down the line” in a way that actually moves the product toward **institutional usefulness** (CMO/Quality/GC), the most useful next direction is:

## Bulk export (first)

Because it immediately unlocks real operator workflows:

* “Give me everything **UNVERIFIED + Forensics + last 30 days**”
* “Export the exact set I’m looking at right now” (filters become a *query contract*)
* It turns the UI from “viewer” into “tooling”

It also forces you to formalize an **export contract** (what’s included, what’s excluded, what’s proof-only), which you’ll reuse later for audit trail.

### Why not audit trail first?

Audit trail is the most *legally* valuable, but it’s best when you have a stable notion of **actor identity** (user/session) and you’ve already defined what an export *is*. Without that, you risk building a log that is correct but not admissible/useful.

---

## Recommended order

1. **Bulk export** (bounded, filter-respecting, proof-safe) ✅ next
2. **Saved views** (turn recurring queries into 1-click presets)
3. **Receipt comparison** (power feature for review workflows)
4. **Audit trail** (once exports + identity are stable)

## What I would ship as Bulk Export v1

**Goal:** export exactly what the operator is viewing (server-side filters), in a safe package, without blowing up memory.

### Backend

* `POST /api/receipts/bulk-export`

  * Body: `{ status?, q?, hasForensics?, killSwitch?, pageSize?, scope }`
  * `scope`:

    * `"current_page"` or `"all_results"`

* Response:

  * `{ exportId, status: "QUEUED" | "READY" }`

* `GET /api/exports/:exportId`

  * `{ status, total, completed, createdAt, expiresAt }`

* `GET /api/exports/:exportId/download`

  * returns a ZIP

**ZIP contents (v1)**

* `receipts.jsonl` (one receipt JSON per line)
* `receipts.csv` (metadata columns only)
* `proof_urls.csv` (receipt_id, proof_url)
* `manifest.json` (filters used + total count + generatedAt)
* `README.txt` (what this is / what it isn’t)

### Frontend

On `/receipts`:

* Add an **Export** button with dropdown:

  * “Export this page”
  * “Export all results”
* If export would include any **PII** or **kill switch** receipts, reuse your existing **Confirm Export** modal logic, but show a short summary count:

  * “PII receipts: X”
  * “Kill switch receipts: Y”
* Show toast:

  * “Export started”
  * “Export ready” (with Download button)

### Guardrails

* Hard cap `pageSize <= 200` already exists; bulk export “all results” must still be bounded:

  * either async job OR stream ZIP generation
* Exports must **not** include interpretation content if kill switch policy blocks it (your current policy is: export allowed; interpretation blocked). So export includes raw receipt + forensic export outputs, but not any derived interpretation fields beyond what’s already in the receipt.
