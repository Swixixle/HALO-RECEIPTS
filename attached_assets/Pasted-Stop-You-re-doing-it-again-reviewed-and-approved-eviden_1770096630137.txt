You wrote:

This is not acceptable as a chain anchor.

Why it fails
	•	It’s not tied to the actual canonical transcript, only to whatever transcript_hash_sha256 is claimed to be.
	•	It’s not tied to issuer identity (key id) or signature.
	•	It’s vulnerable to receipt-id games and reissuance ambiguity.
	•	It doesn’t define whether the chain link is immutable once signed.

Correct approach

A receipt’s link hash must be derived from the same immutable object the signature attests to.

Use one of these two options (pick one now, do not invent a third):

Option A (recommended): Chain on the signed capsule hash

Compute:

receipt_hash = SHA256(c14n(capsule_core))

Where capsule_core is the canonicalized JSON containing at least:
	•	schema
	•	receipt_id
	•	platform
	•	captured_at
	•	transcript (or transcript_hash + canonicalization spec)
	•	previous_receipt_hash
	•	public_key_id
	•	(optionally) redactions metadata

Then:
	•	previous_receipt_hash_sha256 must equal the prior receipt’s receipt_hash.

Signature verifies capsule_core, so chain integrity inherits signature integrity.

Option B: Chain on the signature payload hash

If signature is over a payload signed_payload, then:

receipt_hash = SHA256(signed_payload_bytes)

Same linkage rule.
