## 1) Make `payload_v` a *hard* invariant at write time too

Right now you write `payloadV: 1` manually. That’s fine, but it’s one more place drift could happen later.

Best practice: derive it from the builder so “append can’t lie” even accidentally.

**Pattern:**

```ts
const payload = auditPayloadV1(row);
const payloadV = payload._v;           // <- source of truth
const hash = hashAuditPayload(payload);

await insert({
  ...,
  payloadV,
  hash,
});
```

That way you never end up with `payloadV: 1` while accidentally using `auditPayloadV2()` later.

## 2) Make `unknown_payload_version` deterministic + operator-friendly

You already added this reason — good. Two tweaks:

* Include the **version number** and **seq** in the error payload (sounds like you do).
* Treat it as **BLOCK** (not just a “warn”) in the UI, because it means your verifier literally can’t interpret the chain.

Suggested detail string:

* `No payload builder registered for payload_v=99 (seq=1234)`

## 3) Add a “strict mode” for verify to prevent partial-coverage misunderstandings

Even with your partial semantics work, reviewers love an explicit switch.

* `verifyAuditChain({ limit, strict: true })`

  * If `limit < totalEvents`, return failure with `reason: "partial_coverage"` (or keep ok=false with a detail)
* Default for UI could remain non-strict, but for “Governance / Audit” view you can force strict.

This prevents someone from ever screenshotting “OK” while only verifying first N.

## 4) Migration nuance: existing rows and defaults

If you ever had pre-`_v` rows (v0), the most defensible story is:

* `payload_v DEFAULT 1` is correct **only if** all rows in table are v1 (post-genesis reset).
* If not, do `DEFAULT 0`, backfill appropriately, and keep builder map supporting v0.

Given you’re fresh-genesis now, your choice is consistent.
