Validation should be strict on required fields; tolerate extra fields but store them.

2.2 Verifier request schema (API input)

POST body:

{
  "schema": "ai-receipt/verify-request/1.0",
  "request_id": "optional",
  "receipt_capsule": { ...ai-receipt/1.0 capsule... },
  "options": {
    "verify_signature": true,
    "verify_chain": false,
    "key_registry_mode": "allow_untrusted"
  }
}

2.3 Verifier result schema (API output)

Return:

{
  "schema": "ai-receipt/verify-result/1.0",
  "request_id": "…",
  "receipt_id": "…",
  "verification_engine": {
    "engine_id": "replit-node-verifier/0.1.0",
    "verified_at": "ISO-UTC"
  },
  "integrity": {
    "canonicalization": "c14n-v1",
    "canonical_transcript": "string used for hashing",
    "computed_hash_sha256": "hex",
    "expected_hash_sha256": "hex",
    "hash_match": true
  },
  "signature": {
    "alg": "Ed25519",
    "public_key_id": "…",
    "status": "VALID | INVALID | UNTRUSTED_ISSUER | SKIPPED",
    "reason": "string"
  },
  "chain": {
    "checked": false,
    "status": "NOT_CHECKED | OK | BROKEN",
    "reason": "string"
  },
  "verification_status": "VERIFIED | PARTIALLY_VERIFIED | UNVERIFIED",
  "failure_modes": [
    { "code": "HASH_MISMATCH | BAD_SCHEMA | …", "message": "…" }
  ]
}

Status rules:
	•	if hash_match is false → UNVERIFIED with HASH_MISMATCH
	•	else if signature VALID → VERIFIED
	•	else if signature UNTRUSTED_ISSUER → PARTIALLY_VERIFIED
	•	else if signature INVALID → UNVERIFIED

v1 signature: unless we implement a real key registry, signature should be:
	•	UNTRUSTED_ISSUER (not invalid), with reason: “no key registry configured”

Do not claim signature validity without actual verification.

3) Canonicalization (c14n-v1) — EXACT RULES

We need deterministic hashing.

Input: receipt_capsule.transcript.messages[]

c14n-v1 output string = JSON string of object:

{
  "messages": [
    {"role":"user","content":"..."},
    {"role":"assistant","content":"..."}
  ]
}

Rules:
	•	Only include role and content
	•	Normalize role to lowercase (user|assistant|system|tool allowed but store as given; for hashing include exact normalized)
	•	Preserve content exactly (no trimming)
	•	JSON must be stringified with stable key order (messages, then each message role, content)
	•	No extra whitespace (use JSON.stringify on a constructed object with ordered keys)

This string is what we SHA-256.

	•	Run c14n-v1

	•	Compare
	•	Determine signature status (UNTRUSTED_ISSUER unless registry configured)
