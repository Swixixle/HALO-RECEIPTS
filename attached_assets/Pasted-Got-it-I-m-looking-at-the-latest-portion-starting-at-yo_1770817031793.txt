## Session Logic-Chain Archive — `stableStringifyStrict` Hardening + Payload/Hash Separation

### 2) Primary upgrade: strict, hostile serialization gate (`stableStringifyStrict`)

Objective: eliminate **silent hash divergence** and **runtime-dependent byte differences** by rejecting ambiguous types and unsafe structures *before hashing*.

Implemented strict rejection with **path-based error messages** for:

* `undefined` (forces callers to normalize explicitly; no silent field disappearance)
* `BigInt`, `Date`, `Map`, `Set`, `RegExp`, `Buffer`
* non-finite numbers: `NaN`, `Infinity`, `-Infinity`
* `function`, `symbol`
* non-plain objects / class instances (prevents hidden prototype/state drift)
* circular references (detected via `WeakSet`)
* dangerous keys: `__proto__`, `constructor`, `prototype` (prevents prototype pollution / canonicalization attacks)

**Key operator benefit:** failures point to an exact location (e.g., `$.payload.createdAt`), making remediation deterministic and reviewable.

### 3) Structural separation: payload construction ≠ hashing

Objective: stop “field drift” between append and verify.

Refactor:

* `auditPayloadV1(...)` now **returns only the canonical payload object** (schema-aligned).
* `hashAuditPayload(payload)` now performs:

  1. strict canonical serialization (via `stableStringifyStrict`)
  2. SHA-256 hashing

Then both:

* `appendAuditEvent` and
* `verifyAuditChain`
  use the exact same `auditPayloadV1 → hashAuditPayload` pipeline.

**Invariant enforced:** if append and verify ever diverge, it can only happen in one of two functions — not by silent inline differences.

### 4) Critical hash-compatibility decision: avoid `JSON.stringify` ordering assumptions

You correctly flagged this risk:

* A version of `stableStringifyStrict` that normalizes into an object and then calls `JSON.stringify(normalized)` *implicitly relies on runtime property enumeration behavior*.
* While **Node/V8 preserves insertion order for string keys**, relying on that is a **cross-runtime risk** for audit-grade hashing.

Resolution:

* Keep the **strict type checks** and **path errors** from the hardened approach
* BUT preserve **manual JSON string building with lexicographically sorted keys** (like your previous implementation)

Result:

* Deterministic serialization remains **provably stable independent of runtime object key ordering semantics**
* Hash output remains consistent with prior behavior **for the same allowed inputs**
* Therefore: **no forced chain reset** required *based solely on stringify mechanics*
