## 1) Harden `/health` into two endpoints: “alive” vs “ready”

Even if you already have `/health`, you want this separation:

### ✅ `/api/health` (liveness)

* Must be fast
* Must not hit DB
* Must always return JSON like:

```json
{ "status": "ok", "time": "...", "version": "..." }
```

### ✅ `/api/ready` (readiness)

* Hits DB (light query)
* Optionally checks audit head invariants cheaply
* Returns:

```json
{
  "status": "ok" | "degraded",
  "db": { "ok": true },
  "audit": { "ok": true },
  "time": "...",
  "version": "..."
}
```

**Why:** liveness should never flap when DB hiccups; readiness should.

## 2) Audit verify route: make it “operator-grade”

Since `/api/audit/verify` already exists, check these **four** properties:

### A) It reports partial coverage *explicitly*

If `limit < totalEvents`, the response must clearly show:

* `partial: true`
* `checkedEvents`
* `totalEvents`

### B) It reports where it fails

On failure, return a machine-usable pointer:

* `firstBadSeq` (or equivalent)
* optionally `expectedHash` / `actualHash` if you want

### C) It’s safe to run

Verify route must:

* avoid loading all rows into memory
* do deterministic ordering
* respect a maximum server-side cap even if client requests huge

### D) Auth posture is intentional

Decide and document:

* **Public** verify? usually no.
* **Authenticated** verify? usually yes.
* If authenticated, make sure error is JSON not SPA HTML.

**Minimum schema to standardize**

```ts
type AuditVerifyResult = {
  ok: boolean
  partial: boolean
  totalEvents: number
  checkedEvents: number
  head?: { seq: number; hash: string }
  firstBadSeq?: number
}
```
