Critical Architectural Note (not a blocker, but it must become policy)

You changed schema validation to be more permissive so forensics can detect anomalies. That’s correct, but it introduces a subtle trap:

You must treat schema validation as two phases

Phase 1: Intake permissive (accept more shapes so you can run forensics)
Phase 2: Verification strict (only “verified transcript” can exist if it passes strict schema)

Right now you’ve effectively loosened your “input acceptability.” That’s fine only if:
	•	A receipt can still be marked UNVERIFIED with failure_modes like SCHEMA_INVALID_STRICT if strict verification requirements fail.
	•	based_on and integrity_context prevent pseudo-verification (you already have this).

Directive for P2: formalize this in code as:
	•	parseCapsulePermissive()
	•	validateCapsuleStrictForVerification()

…and ensure based_on: verified_transcript is impossible unless strict validation passes.
