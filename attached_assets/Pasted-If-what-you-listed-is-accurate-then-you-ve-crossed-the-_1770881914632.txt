## 1) CI/CD as a non-negotiable enforcement layer (P0)

You already built the artifacts—now make regressions *impossible* to merge.

### Add these CI gates

1. **Typecheck + unit/golden + E2E**
2. **Demo script gate** (runs `scripts/demo.sh` against a local ephemeral env)
3. **Forensic export/verify gate**

   * export a pack from a seeded DB state
   * verify it offline
4. **Canonicalization drift gate**

   * fail CI if `stableStringifyStrict` / `auditPayloadV1` logic appears anywhere except `server/audit-canon.ts`
5. **Wire-boundary grep guard** (if not already)

   * fail if `observation_type` appears outside the allowlist

**Acceptance criteria**

* A PR cannot merge unless all 5 gates pass.
* CI produces a “proof bundle” artifact (logs + pack + verifier output) attached to the run.

---

## 2) Release packaging (P0 if you’re showing this to anyone external)

Right now you have scripts/docs. Turn them into a **versioned release kit**.

### What to add

* `releases/` structure or GitHub Releases artifacts:

  * `demo-kit-vX.Y.Z.zip` (DEMO_SPINE + demo.sh + sample outputs)
  * `forensic-verifier-vX.Y.Z.zip` (offline verifier only; no server code)
* **Version stamping** everywhere:

  * pack includes `commit`, `semver`, `audit_payload_version`
* **SBOM** (CycloneDX or SPDX) for the verifier package (this matters in hospitals)

**Acceptance criteria**

* You can hand someone a single zip and they can verify a pack with *no* repo access.
* Every pack can be tied to an immutable version/commit.

---

## 3) External anchoring / signed checkpoints (P1 “defensible against privileged rewrite”)

Even if your threat model correctly admits the “privileged DB rewrite” case, procurement will ask: “So how do you address that class?”

### Minimal, high-impact step

* **Signed checkpoints every N events**:

  * checkpoint contains `{seq, hash, ts, previous_checkpoint_hash}`
  * signed with an offline/private key (Ed25519 is fine initially)
* Store checkpoints:

  * separate table + optionally exportable to WORM/S3 Object Lock / external timestamping

**Acceptance criteria**

* If someone rewrites the DB history, you can prove mismatch against checkpoint chain.
* Checkpoint verifier is offline-capable.

*(This is the single biggest “audit-grade” upgrade beyond what you already built.)*

## 4) Regulatory Alignment Matrix (P1 for CMO/GC conversations)

This is what compliance actually buys: mapping, not cryptography.

### Deliverable

* `docs/REGULATORY_ALIGNMENT.md` with a matrix for:

  * **21 CFR Part 11** (audit trails, signatures, record integrity)
  * **HIPAA Security Rule** (integrity controls, audit controls)
  * **SOC 2 (Security/Availability/Confidentiality)** mapping
  * **ISO 27001** control alignment (high-level, honest)
  * **EU AI Act** high-risk logging/traceability posture (careful wording)

**Acceptance criteria**

* Every row has: requirement → feature → evidence artifact (test/doc/output) → limitations.

## 5) PQC roadmap (P2 unless you’re courting very long retention / nation-state buyers)

Don’t overbuild too early, but do the *credible plan*.

### Deliverable

* `docs/CRYPTO_AGILITY.md`

**Acceptance criteria**

* No signature scheme is hard-coded into pack/verifier assumptions.
* Adding ML-DSA later is an additive change, not a rewrite.
