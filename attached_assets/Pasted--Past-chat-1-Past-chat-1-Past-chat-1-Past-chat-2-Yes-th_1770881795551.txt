# 1) Demo Spine (docs + runnable script)

## Deliverables

* `docs/DEMO_SPINE.md` — the “operator runbook” (human-readable)
* `scripts/demo.sh` — the “press enter” runnable demo (machine-executable)

## Demo contract (keep it boring and repeatable)

Your demo should be built around **only** these primitives:

* `/api/health` (liveness)
* `/api/ready` (readiness)
* A path that **causes audit events** (whatever your product’s core action is)
* `/api/audit/verify` (operator verification)

### `docs/DEMO_SPINE.md` structure (recommended)

1. **Prereqs**

   * env vars (API key, base URL)
   * tooling (curl; jq optional)
2. **Step 1: Confirm liveness**

   * curl `/api/health`
   * expected fields + example output
3. **Step 2: Confirm readiness**

   * curl `/api/ready`
   * explain degraded vs down semantics
4. **Step 3: Produce audit events**

   * run 1–2 API calls that create events
5. **Step 4: Verify chain**

   * call `/api/audit/verify?limit=…`
   * highlight `partial`, `checkedEvents`, `firstBadSeq`
6. **Step 5: Show failure mode**

   * either: demonstrate rate limiting behavior
   * or: export + tamper + offline verify (if you want the knockout in-demo)

### `scripts/demo.sh` must:

* Fail fast (set `-euo pipefail`)
* Print commands before running them
* Validate it got JSON (not HTML fallback)
* Never require manual editing mid-run

Example “command runner” pattern:

```bash
run() { echo; echo "▶ $*"; eval "$*"; }
need() { command -v "$1" >/dev/null || { echo "Missing $1"; exit 1; }; }
```

**Acceptance criteria**

* From fresh clone, one command runs the full demo:

  * `./scripts/demo.sh`
* It produces **deterministic** output sections (even if IDs differ).

# 2) Forensic Export Pack (portable evidence artifact) + Offline Verifier

This is the “courtroom move”: **no DB**, no server, no “trust me.”

## Deliverables

* `scripts/export_forensic_pack.ts`
* `scripts/verify_forensic_pack.ts`
* `docs/FORENSIC_EXPORT_PACK.md`

## The pack format (minimum viable, but defensible)

### Pack JSON schema (conceptual)

```json
{
  "pack_version": 1,
  "exported_at": "2026-02-12T18:22:00Z",
  "system": {
    "name": "…",
    "env": "…",
    "commit": "…",
    "audit_payload_version": 1
  },
  "range": { "from_seq": 1, "to_seq": 1200 },
  "head": { "seq": 1200, "hash": "…" },

  "events": [
    {
      "seq": 1,
      "ts": "…",
      "type": "…",
      "payload": { "...": "..." },
      "prev_hash": "…",
      "hash": "…"
    }
  ],

  "manifest": {
    "events_count": 1200,
    "first_seq": 1,
    "last_seq": 1200,
    "pack_hash_alg": "sha256",
    "pack_hash": "…"
  }
}
```

**Key rule:** `pack_hash` must be computed over a **canonical serialization** of the pack *excluding* `manifest.pack_hash` itself, using your strict canonicalizer.

## Exporter rules

* Export a **contiguous range** by default (cursorable via `--from` `--to`)
* Embed the **head** you expect for that range
* Compute `pack_hash` last
* Write to `out/forensic-pack.<from>-<to>.<timestamp>.json`

**Do not** embed secrets, raw PHI, or anything outside what’s already inside audit events.

## Offline verifier rules

Verifier must:

* Validate basic shape (pack_version, events[], manifest)
* Recompute **every event hash** from its canonical `auditPayloadV1()` (or your equivalent)
* Validate `prev_hash` chain continuity
* Validate that the last event hash equals `head.hash`
* Recompute `pack_hash` and compare to manifest
* Return:

  * `ok`
  * `checkedEvents`
  * `firstBadSeq` (or null)
  * `reason` (short, operator-readable)

### Output example

```json
{
  "ok": false,
  "checkedEvents": 842,
  "firstBadSeq": 843,
  "reason": "hash_mismatch"
}
```

**Acceptance criteria**

1. Export → verify offline passes.
2. Single-byte edit inside any event → verify fails with the correct `firstBadSeq`.
3. Delete a middle event → fails with “chain break” at the first missing link.
4. Modify `manifest.pack_hash` only → fails “pack_hash_mismatch”.

# 3) Canonicalization: enforce single source of truth

This is the one place teams accidentally create fatal divergence.

## Hard requirement

Your exporter + offline verifier must import the **exact same** canonical hashing functions as the live server. If you can’t share the full server module (DB dependencies), split **pure functions** into a shared module.

Recommended structure:

* `server/audit-canon.ts` (pure)

  * `stableStringifyStrict(value)`
  * `auditPayloadV1(eventLike)`
  * `hashAuditPayload(payload)`
* `server/storage.ts`

  * imports from `audit-canon.ts`

Then scripts import from `server/audit-canon.ts` (not storage).

**Acceptance criteria**

* There is **no duplicated** stable stringify / hash logic anywhere.
* One implementation, one test suite, used by server + scripts.

# 4) Threat Model v2 (make it procurement-grade)

## Deliverable

* `docs/THREAT_MODEL.md` (or v2 section appended)

### Required sections (minimum)

1. **Assets**

   * audit integrity, operator trust, chain-of-custody, API key security
2. **Adversaries**

   * external attacker, malicious insider, negligent operator, compromised CI
3. **Trust boundaries**

   * client ↔ server, server ↔ DB, CI ↔ artifact publishing, offline verifier
4. **Threat–Mitigation Matrix**

   * at least 10–12 threats
   * each threat has: attack, impact, mitigation, residual risk
5. **Operator misuse scenarios**

   * “verified ≠ clinically correct”
   * partial verify misread
   * cursor verify misused as full verify
6. **Residual risk**

   * explicitly call out what you *do not* protect against (and why)

**Acceptance criteria**

* A GC can quote it against you and you still win.
* It is explicit about non-goals and privilege assumptions.
